# UI Widgets

**Last Updated:** October 8, 2026

Letter IRL registers six OpenAI Apps SDK widgets as MCP resources with `ui://` URIs and `text/html;profile=mcp-app`. Widget template URIs are versioned (`ui://widgets/<name>.html@v<N>` via `src/mcp/widgetUris.ts`) because the native mobile apps cache widget metadata aggressively (issue #235); bump `WIDGET_TEMPLATE_VERSION` on any widget change — a digest-pinning test enforces this — and the legacy unversioned URI stays registered as a transition alias for stale clients. Tool results keep model-facing data in `structuredContent` and send large render payloads, such as preview HTML and compressed letter-image previews, through widget-only `_meta`.

Two more template names serve an existing card rather than a new widget (`WIDGET_VARIANTS` in `src/mcp/registerTools.ts`, #411): `LetterHeaderImagePreviewCard` and `LetterInlineImagePreviewCard` both serve `LetterPreviewCard.html`, one for each image letter tool. The server stamps every preview template with the tool that draws it, as `<meta name="letter-irl-preview-tool">`, because a card cannot otherwise tell which preview to repeat: the host passes no tool name, and the two image letter tools take identical input. Only the preview templates carry the stamp, and the versioned variant URIs are listed in `resources/list` next to the cards'. `LetterPreviewCard` is stamped only at v32 and later (`previewToolFor`). Before v32 all three letter tools pointed at it, and an image call may carry no image arguments at all, so its legacy URI and older versions go out unstamped.

## Registered Widgets

- `LetterPreviewCard`: Shows text-only, header-image, and enclosed-image letter drafts. Reads letter preview HTML from `_meta.previewHtml`, displays delivery/cost context, and can call `send_letter` only after the user explicitly confirms. For a preview drawn by our own renderer (#534), whose document's body carries `data-renderer`, it shows the page as it prints: the SVG, with the addresses where PostGrid stamps them, which a select enlarges to the card's width. Only the elements and attributes the renderer draws reach the card, each value checked: no handler, style, paint server, filter or link but the page's own outlines and embedded PNG or JPEG images. Every id is prefixed `lirl-page-`, so a page cannot stand in for one of the card's controls. These rules live in `widgets/shared/pages.js`, which both preview cards use. The pages are a labelled group, so the page's title (the letter's text) stays readable to screen readers, and an Enlarge button beside the page keeps its state across the card's re-renders. A gift send's card is the second page, its border a rounded, stroked `rect` and its QR plain `rect`s. Every other preview, a legacy one, gets a mockup drawn from the text in the preview's `letter-body` and `sign-off` elements; a renderer preview keeps those too, hidden, for a card cached from before.
- `PostcardPreviewCard`: Shows the postcard's front from `_meta.previewFrontHtml`, with the back mocked up from the message and addresses, then can call `send_postcard` only after explicit user confirmation. For a postcard our renderer drew (#534), `_meta.previewHtml` carries the postcard as it prints, and the card shows its two pages instead: the front, as its layout draws it (#594: the picture to the edges, in a white border over its caption, or under "Greetings from" and its place), and the back, the message in its left half and the addresses where PostGrid stamps them. They are cleaned by the same shared code as the letter card's page, each in a labelled group. The front's title, which screen readers speak, is its caption or greeting, or "The front of the postcard" when it has none.
- **Both preview cards recover from a lost preview call (#411).** On ChatGPT web, a preview call approved with "Allow once" can vanish: no request reaches the API, yet the host draws the card with no result and the model says the preview is ready. A card with no result waits 25 seconds for a text-only letter, or 45 seconds for an image letter or a postcard, so that a slow but live call can still deliver its own result. A text-only preview checks two addresses in turn, each allowed 10 seconds, and an image preview first downloads its image. A postcard asked for two or more photos (`images` or `imageUrls`, #616) waits 30 seconds longer, once, since its photos download one at a time within a budget of 30 seconds between them. The card then shows "No preview is showing on this card" with **Create my preview**. Under the button, or under the advice when the card offers no button, a tip says that with Instant selected ChatGPT sometimes doesn't run an action you approved, and that a higher thinking effort can help. On 2026-09-17 every approved call lost on development had Instant selected, while both approved calls at Medium thinking effort ran. A card cannot tell which model is selected, because neither `window.openai` nor the `_meta` ChatGPT sends carries it, so the tip is worded for Instant users and shown on every card whose wait ran out. A reopened card does not show it: that card is empty because the host does not replay results, not because a call was lost. Nor does a card in any other app, since the tip is about ChatGPT (#474). The button repeats the stamped tool through `callTool` with the host's `toolInput`, unchanged, and draws the result through the normal render path. The card never calls by itself. After 60 seconds without an answer the button can be pressed again. Whichever preview arrives first is drawn, and any later one is left unused. ChatGPT web returns `_meta` to a card's own call, so the preview is drawn in full (checked on development on 2026-09-17). Without `_meta`, the letter card would draw the text from the arguments, and an image letter would show "Image not shown on this card" where its image would be. The card offers no button, only advice to ask again in the chat, in these cases:
  - the page has no stamp;
  - the host passed no usable arguments;
  - the host passed an image in a form other than the file object the server reads, and the card cannot offer to pick the image again (below);
  - a postcard asked for a collage whose `images` or `imageUrls` hold anything but file objects with an address or `https` links (#616): the server would refuse it, by its place, on every press, and a card cannot pick several photos again;
  - the host cannot call tools;
  - a text-only stamp arrives with image arguments.

  **An image the card cannot pass back (#414).** ChatGPT web passes an image attached or generated in the chat to the card as a sandbox file path, which the server cannot open. For an image letter or a postcard with such an image argument, or with an `imageUrl` that is not an `https` address and no usable file object beside it, the card (unless the call also names a collage, which one picked image cannot repair, #616) offers **Choose from library** (`selectFiles`) and **Upload the image** (a file input, then `uploadFile`; JPEG, PNG or WebP up to 10 MB) in place of **Create my preview**. Each button appears only when the host provides that call as well as `callTool` and `getFileDownloadUrl`. The card then gets the file's download link and repeats the stamped tool with the host's arguments, leaving out `image` and any `imageUrl` and adding the link as `imageUrl`, as the upload card hands images over. The drawn result, timeouts and first-preview-wins rule are those of **Create my preview**. If the library picker, the upload or the link request has not answered after two minutes, the buttons come back so the person can try again; a new attempt replaces the waiting one, and a waiting one that answers first carries on. A preview, or a kept order, that arrives while the person is picking ends the pick.

  A host result that arrives later replaces the card's own draft until the card first tries to send it or pay for it, whether or not that attempt succeeds. Both drafts hold the same mail, and the host's is the one the model knows, so a send from the card and a send from the chat land on one draft, which the server sends once. A send that failed on the card's side may still have gone out, and the server recognises a repeat only for the same draft, so the card never switches after an attempt. Two drafts can still both be sent when the card sends its own before a slow host result arrives and the user then confirms a send in the chat (#412).
- **Both preview cards handle a refused send or checkout (#412).** A send or checkout the server refuses comes back as an error result, and the cards no longer read it as success. For the same mail sent, paid for or awaiting payment in the last 24 hours, the card says what went out and when, from `_meta["letterirl/duplicateMail"]` or, without it, from the `Possible duplicate:` text. On ChatGPT web only the text arrives: a card's own call gets its `_meta` back when it succeeds, but not when it is refused (checked on development on 2026-09-17, DUPLICATE-01 in [manual-tests.md](manual-tests.md)). So the card says only that the same mail went out recently, and the text is what makes it work. It then turns the button into **Send another copy** or **Pay for another copy**; the next click passes `sendAnotherCopy: true`, and the label survives a re-render. Any other refusal shows as a failure with the server's text.
- **Both preview cards offer the arrival date (#535)** while the preview names the dates on offer (`arrivalWindow`, only while `LETTER_IRL_ARRIVE_BY_ENABLED` is on) and the host lets the card call tools.
  - **Arrives by:** a row under Delivery with a date field, bounded by those dates, and **As soon as possible**. A preview made with `arriveBy` starts from its date.
  - **Choosing a date** calls `set_arrival_date` with the draft and the date; **As soon as possible** calls it without one. Send, Pay & Send and the field wait meanwhile, the field showing the date being set. Setting one acts on the draft, so a late host result does not replace a draft the card made itself. The answer's `schedule` and `deliveryEstimate` redraw the row, the Delivery line and the note under it: "Mails Tue, Oct 6 · cancel free until then". The send button then reads **Schedule Letter** (or **Schedule Postcard**, or the gift's).
  - **A refused date** leaves the dates as they were. A refusal naming a new earliest or latest date moves the field's bounds to it: what is on offer moves on at noon New York time on a business day and at midnight, so a card held open goes out of date.
  - **Sent with a date,** the card says what the send answers, not what it thought of the dates, which the chat may have changed meanwhile: `currentStatus` `scheduled` with its `schedule` (#535). Then the card shows **Scheduled**, **Letter Scheduled**, the mail date, and **Cancel this letter** while the answer says `cancellable`. Pay & Send mail waits without Cancel: "Mails Tue, Oct 6 · to cancel, email support@letterirl.com". Anything else, a dated send the outbox took at once included, reads **With the printer**.
  - **Cancel:** a first press asks; a second calls `cancel_scheduled_mail` with `confirm: true` and shows its message: what came back. A refusal that leaves nothing to cancel ends the offer, saying which: gone to the printer, going now, not scheduled, or Pay & Send. Any other refusal is shown as it is and may be tried again. As with every card call, the model does not see these results, so the card shows each one.
  - **The field goes** when a checkout starts, as it does once one exists. The notes under the field and on Scheduled are announced to screen readers (`aria-live`).
  - **Known limit:** a date set or cleared from the chat while a card is open is not seen by that card before its send, so its label can be out of date. The send's answer, and the confirmation page where it applies, say what happened.
  - **One script for both cards:** `widgets/shared/arrives.js` (`window.letterIrlArrives`), inlined like the bridge.
- **The letter card offers its stationery (#563)** while the preview names the stationery its page was drawn in (`stationery`, only while stationery is offered) and the host lets the card call tools. Postcards take none.
  - **Style:** a row under Arrives with **Classic**, **Monogram**, **Botanical**, **Celebration**, **Typewriter** and **Handwritten**, the one the page is in pressed (`aria-pressed`).
  - **Choosing one** calls `set_stationery` with the draft and the theme. Initials or a headline this card saw with that theme on this draft are sent again with it, so a headline survives a trip to another style and back. Send, Pay & Send and the row wait meanwhile: the theme being set shows pressed and the others dimmed (`aria-disabled`, not `disabled`, so the pressed button keeps keyboard focus). Setting one acts on the draft, as a date does.
  - **The answer:** the page in its `_meta.previewHtml` replaces the preview's, and its `stationery` presses the row. An answer without the page keeps the last one and says the style is changed but its page did not come back. An answer without its stationery, or about another draft, says the style may have changed. A refusal leaves the style as it was, shown under the row (`aria-live`).
  - **The row waits** while the card sends the letter, and is usable again after a send that fails. It goes once the letter is sent and when a checkout starts, and comes back with the Arrives row when a checkout is refused before it opens. The theme is remembered for the account's next preview, as one the model chose is.
  - **Shown its preview again** (Claude hands a reopened card the preview's first answer): the card's `get_draft_status` answer names the draft's style now, with its page in `_meta`, and the row presses that style and the card draws that page.
  - **Known limit:** a style set from the chat while a card is open is not seen by that card before its send, as for dates: the card shows the page it last drew, and the send sends the draft as it is.
  - **One script:** `widgets/shared/style.js` (`window.letterIrlStyle`), inlined like the bridge.
- **The letter card's Signature switch (#608 part 4b)**, beside the styles, while the Style row shows and the preview says a signature is saved (its `signature`, with any `source` but `none_saved`; a preview asked to leave it off still reads whether one is saved, #615 review round 1).
  - **The switch** is a button with `role="switch"` and `aria-checked`, reading **On** or **Off**: both states can be pressed, so it is a pill rather than a link.
  - **Pressing it** calls `set_letter_signature` with the draft and the other state. It shares the Style row's wait: Send, Pay & Send, the styles and the switch wait meanwhile, the switch showing the state being set (`aria-disabled`, not `disabled`). The answer's page replaces the preview's, its price and pages are the card's (the band can run the letter on to a page), and a refusal (no room) is said under the row, which keeps the switch and page as they were. A signature removed since the preview (`SIGNATURE_NOT_SAVED`, written for the model) is said in the person's words, and the switch is put away. A press a host still delivers to the hidden switch does nothing.
  - **Shown its preview again,** the card's `get_draft_status` answer says whether the draft is signed now (`signature`), and the switch takes it.
  - **In the studio** it sits in the Style tab under the styles. It lives in `widgets/shared/style.js` with them.
- **The letter card's envelope reveal (#576)**, while the preview's `_meta` carries `letterirl/envelopeReveal` (`LETTER_IRL_ENVELOPE_REVEAL_ENABLED`, on in development only; `cardSwitches` in `src/mcp/registerTools.ts`):
  - **Opening:** the first time the card shows a draft's page, a #10 window envelope sits over the page's top third, its windows where PostGrid stamps the addresses, and the page unfolds out of it (0.8 s). A host redraw, a restyle or a date change never plays it again.
  - **Sealing:** a successful send or schedule folds the page back in (0.7 s), and the sealed envelope stays, its windows showing the addresses; the page's box shrinks to the envelope's height. A press on it, or **Show the letter**, shows the page again. A refused send changes nothing.
  - **Never in the way:** every motion stays inside the page's box, so the card never grows; Send and the rows work throughout. A redraw that changes nothing (a host's, or the card's own after `get_draft_status`) keeps the page view, so the motion plays on; a gift letter's two pages fold to one envelope, the clip being the envelope's height. With reduced motion nothing moves: the page shows at once, and a sent letter is sealed at once. A host that never ends the animation still sees the card settle (1.6 s).
  - **One script:** `widgets/shared/envelope.js` (`window.letterIrlEnvelope`), inlined like the bridge. Postcards have none.
- **The letter card as a studio (#580)**, while the preview's `_meta` carries `letterirl/studioCard` (`LETTER_IRL_STUDIO_CARD_ENABLED`, on in development only; `cardSwitches` in `src/mcp/registerTools.ts`). Without it the card is laid out exactly as before.
  - **Layout:**
    - A header naming the letter ("Letter to Sam Rivera") with the status pill. Under it, where the letter stands (Draft, Paid, Sent, Cancelled or Expired) and its town ("Springfield, IL 62701").
    - The page beside three tabs, **Style**, **Words** and **Delivery**, stacked below 560 px.
    - A footer with the cost, a summary and Send.
      - The cost reads "1 letter", "Pay & Send USD 5.99" for mail no pack pays for, "Paid USD 5.99" once a Pay & Send order is paid, or "Free: a gift letter".
      - The summary gives the stationery, the ink ("black and white", or "colour" for a letter with its picture, which prints in colour), and where the letter is: when it mails, "held until" its mail date, "with the printer", cancelled or expired.
  - **Once sent:** the dates are the server's (`get_draft_status`) or the send's own, never the Arrives row's, since the chat may have changed them.
  - **Pay & Send:** an order is followed by `get_purchase_status`: Paid (held until its mail date, if it has one), then Sent and with the printer. An order that stops says so and promises no mail: the payment did not go through, refunded, on hold, or cancelled.
  - **Expired:** an expired preview holds no date any more.
  - **Nothing new to press:** the tabs hold the card's own rows, notes and buttons, moved from `#studio-template`'s slots. **Style** has the Style row (named Stationery there) and the layout. **Delivery** has the Arrives row, Scheduled with Cancel, the Mail choice (below), the delivery line and the draft or order id. Each control calls its tool as before (Principle 2). **Words** shows the letter's text as the call gave it, or as the card last set it. To change it, the person asks in the chat, or, while room to write is offered, uses the editor (below).
  - **The Mail choice (#648):** while certified mail is offered, a letter that is not a gift letter shows **First-Class**, **Certified** and **Certified + e-receipt** (the electronic return receipt, which Letter IRL does not send on) on the Delivery tab, the one it travels by pressed. The services come in the preview's `_meta.mailServices`, card-only, which the server sends only while certified mail is offered and never for a gift letter; without it, with one service, or for a preview that named no stationery (the Style row draws it), there is no row. A press calls `set_mail_service` with the draft and the service, the pressed one too, so a card that did not hear the chat change it (ChatGPT's) hears the draft as it is. Not while the card sends the letter or starts paying for it. Meanwhile the pressed service shows, every choice and Send wait, and a second press is ignored. The answer's terms and how the letter travels are taken as a restyle's are, so the cost, the summary, the pay note, the Delivery line and the buttons follow it, and the pressed service is the one the answer names, not the one pressed. The answer gives the pages with the price, so a letter the chat lengthened unheard shows its length; how full the pages are is card-only, and a change of service leaves the page as it is, so the card keeps it from its last terms or the preview. A refusal is said in the person's words (the server's is written for the model; the connection's unknown-tool error, once certified mail is off, says it is not available), and a refusal, or an answer for another draft or without terms, is said in the Mail row's own note on the Delivery tab (the Style note is on another tab); the service stays as it was. A status or a restyle that says how the letter travels moves the pressed service with it. Once the letter is sent, paid for, or the card is on another draft, there is no row.
  - **Saved designs (#649):** while designs are offered, the Style row also has a button for each of the person's saved stationery designs, after the themes, named as they saved it (drawn as text, never markup). The designs come in the preview's `_meta.stationeryDesigns` (`designId`, `name`, `design`), card-only, which the server sends only while designs are offered and the page is drawn in stationery; without them there are no design buttons. A press calls `set_stationery` with `stationeryDesignId`, carrying back the headline and initials the card last saw with that design, and waits as a theme's press does; the answer must name that design (`theme: custom` with its `designId`), or the card says the style may have changed and keeps it. The row presses a design by its id, or, for a `get_draft_status` answer, which names a design without its id, by its name. A letter drawn in a design shows the row (a design is a stationery the card can show), and the summary and the Words tab name the design by its name. A design saved in the chat after the preview has no button until the next preview.
  - **The first tab:** Style, or Delivery once the letter has a date, until the person picks a tab. A send with a date shows Delivery, where Cancel is.
  - **Tabs:** `role="tablist"`, named by the header, with one tab in the tab order, arrow keys, Home and End.
  - **Pages:** a letter of more than one page (a gift letter's card page) shows one page at a time, with **Next page**. A restyle keeps the page shown; sealed in its envelope, the letter shows its first page. **Enlarge** spreads the page across the card.
  - **Height:** about 580 px at Claude's 736 px width, under the frame Claude stopped at on 2026-09-27 (about 700 px).
  - **One script:** `widgets/shared/studio.js` (`window.letterIrlStudio`), inlined like the bridge, in both preview cards.
  - **How full the letter is (#586):** while the words can be changed in place (room to write, or the words editor alone, #647), the Words tab says how full the letter's pages are, from `_meta.pageFit`. For one page, that is the room left in about how many characters. For two or three pages, it says how they print. The summary names a longer letter's pages, and the cost is its Pay & Send price. The Style row keeps the price and pages a restyle or a `get_draft_status` answer gave (`styleRow.terms`), and the card draws them over the preview's own (`withTerms`), so it shows one price everywhere. A status answer lays nothing out: the fit line keeps the preview's count while the draft's page is still the preview's, and says nothing of room once the chat has changed it.
  - **Changing the words (#586, #647):** where the Style row shows, so only while stationery is offered too (`LETTER_IRL_STATIONERY_ENABLED`), while the words can be changed in place (room to write, or the words editor alone, `LETTER_IRL_WORDS_EDITOR_ENABLED`; the preview's `_meta.pageFit` says so), and while the draft is still a draft, the Words tab offers **Change the words**. It opens the letter and its sign-off in two boxes, with a line counting the room left as they are written, from the last count less what was typed since, and in a gift letter's words that one page is all it has. **Update the page** calls `set_letter_words` with the version of the words it started from (`wordsVersion`); the page, the price, the fit and the words it gave become the card's, and its message says what changed. A refusal is said under the boxes, which keep the words. A refusal of words the card had not seen (`WORDS_CHANGED`: the chat changed them, or the preview carried no version) is written for the model, with the whole letter, so the card says instead that its copy is out of date, and the person asks in the chat or makes the preview again; it is found anywhere in the text, as a host may wrap it (#434). The card fetches nothing to catch up: the server's version check is what keeps a change made elsewhere from being overwritten. An earlier design that fetched the draft's words on opening and after a refusal drew a finding in three review rounds running and was removed (#593 review round 3). A status answer's words (`bodyText`, `signOff`, `wordsVersion`) are the Words tab's too. **Cancel** puts them back, and focus returns to **Change the words**. The room line describes the letter's box (`aria-describedby`), rather than speaking at every keystroke. The editor lives in `widgets/shared/style.js` with the Style row: they share the draft, one wait (`busy`) and the page, so a change waits for the other, and neither runs while the card sends or pays (`hold`). After a change of words, a status answer sent before it is refused as older (`restyled`).

- **Both preview cards keep what they did in `widgetState`** as `{v: 1, draftId, sent?, checkout?, orderId?, checkoutUrl?, schedule?, cancellable?, cancelled?}`: the draft shown, a successful send, or a created checkout with its `https` link. A reopened card that only showed a preview offers **Create my preview** at once, or the image buttons for an image it cannot pass back, because no result is coming. Its message says that if the mail was already sent, for example from the chat, there is nothing more to do.
- **Where the host keeps no state for the card, the card asks the server instead (#474).** MCP Apps has no `widgetState`, and Claude hands a reopened card the preview's result again, so the card would otherwise offer Send for mail that has gone. On a host's result the card calls the card-only `get_draft_status` once per draft ([tool-apis.md](tool-apis.md)). Its answer also carries the draft's arrival dates and delivery estimate (#535), so a card shown its preview's first answer again draws the dates the draft has now, with the Delivery line to match. For a sent draft it says where the order stands, from its letter, never the draft's dates (`orderStatus`): **Scheduled** with **Cancel** while it waits for its mail date and can be cancelled, without Cancel for Pay & Send; **Cancelled** once cancelled, from the card, the chat or the website; **With the printer** once the outbox has taken it.
  - **Sent:** the pill says **With the printer**, the ID row shows the order, a note says the mail has already been sent, and nothing is offered to press. The preview stays, because the host gave it again.
  - **Expired:** the pill says **Preview expired**, a note asks for a new preview, and nothing is offered.
  - **Ready, not found, or no answer:** the card stays as the host gave it.
  - Both answers are final, so one that arrives late still holds. A send this card is making keeps the pill and the buttons meanwhile, and an earlier failure to send is cleared by a sent answer.
  - The card never asks in ChatGPT, which keeps the card's own state, nor about a draft it made itself.
- `ImageUploadCard`: Opens a file picker fallback for image handoff problems. **In ChatGPT** it uploads the photo to ChatGPT's file store (`uploadFile`; JPEG, PNG or WebP up to 10 MB) and calls `confirm_uploaded_image` with the resulting `imageUrl`. When the host exposes `selectFiles` (plan/region-gated), it also offers a "Choose from Library" button that picks a file already in the user's ChatGPT Library and reuses the same confirm/follow-up handoff without re-uploading; because pick-time download URLs are temporary, a fresh URL is re-resolved via `getFileDownloadUrl` when the user confirms.
  - **In any other app (Claude), the card sends the photo itself (#474, phase 3).** MCP Apps gives a card no file store. The card decides by the kind of host, not by what the host offers at that moment, so ChatGPT always keeps its own path.
  - **Only while the server allows it.** `upload_image` says `cardUploadAvailable: true` only while `LETTER_IRL_CARD_UPLOAD_ENABLED` is on. Until then, the card hides **Select Photo** and says photo upload isn't available in this app yet, and to use a link to the photo instead.
  - **Shrunk first.** The card draws the photo on a canvas, on white, at most 2400 px on its long side, and makes a JPEG at quality 0.88. Because it shrinks the photo, it takes originals up to 25 MB.
  - **Sent in chunks.** The base64 goes in chunks of 512 Ki characters through the card-only `upload_photo_chunk`, one after another under one upload id ([tool-apis.md](tool-apis.md)). With each chunk it sends the upload's context only when that is `postcard`, `header_image` or `inline_image`, since a result from before the server read the context may carry the model's own words. A chunk whose answer is lost is sent once more; the server answers a repeated chunk as it did the first time. A refusal is shown in the server's words, and any other failure as "Upload failed. Please try again."
  - **Then the preview.** The server keeps the photo as the account's one uploaded photo and makes it the account's recent upload, so the next preview with no image uses it. The card then sends `ui/message` asking for that preview, for example "Make the postcard with the photo I just uploaded." If the host will not take the message, the card shows that sentence for the person to send. There is no link to show, because the photo has none.
- `GetStartedCard`: Presents onboarding guidance, purchase prerequisite messaging, and example prompts for new users.
- `ImageRoutingCard`: The `generate_image_for_mail` result, in one of two states. **Generated**: the image made in-turn with one of the user's Letter IRL image generations, a credit line with the generations remaining, and the image URL with a Copy button so it can be handed to a preview tool. **Redirect** (no generations left, the global daily ceiling reached, generation turned off or unconfigured, or the provider failed): an explanation and the prompt with a Copy button, so the user can resend it without mentioning Letter IRL and let ChatGPT's built-in generator make it free. On desktop (`redirectStyle: "handoff"`) the card says replying "go ahead" is enough; on mobile (`"resend"`) it asks for the copy-and-resend. It deliberately does not call `sendFollowUpMessage` (see [learnings/generate-image-removal-decision.md](learnings/generate-image-removal-decision.md)).
- `PackCheckoutCard`: Shows a letter pack checkout with the pack, the price, the order id and the Stripe link as a real anchor. Rendered without a tool result (ChatGPT has dropped the first consequential call after "Allow once", issue #322), it waits five seconds and then offers to create the checkout itself through `callTool`, using the pack from `toolInput` when present and otherwise listing the packs via `list_letter_packs`. Its empty state carries the same Instant tip as the preview cards. While a checkout is open it polls `get_purchase_status` in the preview cards' visibility-gated shape (3 s for the first minute, then 15 s, for ten minutes, plus a Check status button) and replaces the link with the outcome: paid with the letters added, still being credited, expired or failed with a new-checkout offer when the pack is known, or the server's message for refunds and holds. A checkout the card created, and any status it has shown, take precedence over a later `openai:set_globals`. The card keeps the order it shows and the last status it saw in `widgetState`. A reload, or the return page's link back into the conversation, reopens the card instance. A reopened instance resumes from that kept state whether or not the host replays the tool result, provided the host delivers the kept state no later than the result. It draws the kept order and status at once, reads the status once straight away when it can call tools, polls at the slow interval for up to nine minutes, and never opens the checkout by itself. Its link points at the API's `/purchase/start` page (`checkoutStartUrl`) and a tap goes through `openExternal`, so for the allowlisted API origin ChatGPT appends the `redirectUrl` that the start page keeps in a same-site cookie and the return page turns into **Back to your conversation** (#372); a plain fallback link appears if the host call opens nothing. Both pages log one line per request (`purchase.start`, `purchase.return`) carrying presence, host and outcome fields only, never the link, the cookie or the checkout session.

Every card's header shows the website's mark, the logo in its navbar. `scripts/build-widget-logo.ts` makes the website's JPEG transparent, writes a light and a dark PNG (the dark one lifts the blues) to `assets/brand/png/`, and inlines both as `data:` URIs in each widget's `.logo` rules. A test checks that all six widgets carry exactly those files. See `assets/brand/README.md`.

## Runtime Bridge Notes

- **The shared card bridge (#474).** A card marks the spot with `<!-- letter-irl:host -->`, and the server inlines `widgets/shared/host.js` there (`inlineHostBridge`, `src/mcp/widgetHost.ts`). The same way, `<!-- letter-irl:pages -->` brings in `widgets/shared/pages.js`, our renderer's pages and their cleaner (`window.letterIrlPages`, #534), `<!-- letter-irl:arrives -->` brings in `widgets/shared/arrives.js`, the arrival date's picker and Cancel (`window.letterIrlArrives`, #535), `<!-- letter-irl:style -->` brings in `widgets/shared/style.js`, the letter card's Style row (`window.letterIrlStyle`, #563), and `<!-- letter-irl:envelope -->` brings in `widgets/shared/envelope.js`, its envelope reveal (`window.letterIrlEnvelope`, #576). This happens both in `resources/read` and on the `/widgets` debug route. The card then talks only to `window.letterIrlHost`: `theme`, `toolInput`, `toolOutput`, `toolMeta`, `widgetState`/`setWidgetState`, `callTool`, `openLink`, `sendMessage`, ChatGPT's file store (`uploadFile`, `selectFiles`, `getFileDownloadUrl`) and `onChange`.
  - **Values** come back as the host gave them: `null`, or `undefined` in ChatGPT, until there is one, so a card can still tell no result from an empty one.
  - **A capability exists only where the host has it.** `callTool`, `openLink`, `sendMessage`, `setWidgetState` and the file store are present only when the host provides them, so a card's check such as `typeof host.selectFiles === "function"` keeps its meaning.
  - **In ChatGPT** it wraps `window.openai` as the cards always used it, reading it at the moment of use. A value, a capability, or even a replaced `window.openai` that ChatGPT sets after the page loads is seen at the next check (phase 3). The upload card relies on this for `selectFiles`, which can arrive late.
  - **Elsewhere** (Claude, VS Code) it speaks MCP Apps (spec 2026-01-26) with the frame's parent:
    - `ui/initialize`, then `ui/notifications/initialized` after the reply;
    - the `tool-input`, `tool-result` and `host-context-changed` notifications;
    - `tools/call`, `ui/open-link` and `ui/message` (content as an array);
    - `size-changed`, plus answers to `ping` and `ui/resource-teardown`.
  - **Where MCP Apps has no equivalent:** `widgetState` is always empty and there is no `setWidgetState`, so a card keeps nothing across a remount there. ChatGPT's file store and `openExternal`'s `redirectUrl` are absent. So the preview cards offer no image picker, and the upload card sends the photo itself.
  - **Display modes (#662).** A card that can be shown larger lists its modes on `<html data-display-modes="inline fullscreen">`. The bridge then offers `displayMode()` and, where the host has one of those modes besides inline, `requestDisplayMode(mode)`, which answers `{ mode }` with the mode given. In ChatGPT that is `window.openai.requestDisplayMode({ mode })`. In MCP Apps the card's modes go in `ui/initialize`'s `appCapabilities.availableDisplayModes`, the request is `ui/request-display-mode`, offered only when the host context's `availableDisplayModes` has the mode, and a change arrives as `host-context-changed`. A card without the attribute declares and is offered none. Only `LetterHomeCard` lists modes so far.
  - **Plugin Extensions in ChatGPT (#665).** Model context (`ui/update-model-context`) and deep links (`hostContext["openai/deepLink"]`) are MCP Apps features that `window.openai` does not carry: in ChatGPT the home said it could not share a selection, and a deep link never reached it. A card that needs them says so on its `<html data-plugin-extensions>`. In ChatGPT the bridge then also sends `ui/initialize` to the frame's parent and takes only two things from the reply: the host context, merged over `window.openai.hostContext` (with later `host-context-changed`), and the capability to update model context (`hostCapabilities.experimental["openai/modelContext"]` or `updateModelContext.text`). Everything else, tool results included, stays on `window.openai`. A host that never answers changes nothing. Only `LetterHomeCard` asks, while its flag keeps it off in production; the letter card's own share (#650) waits for the DEV probe.
  - **Cards on the bridge:** `GetStartedCard` (phase 1), then `LetterPreviewCard` and `PostcardPreviewCard` (phase 2a), then `ImageUploadCard` (phase 3). The pack checkout and image routing cards still call `window.openai` directly, because Claude is not offered their tools (#475, #490).
- **Card address and copy per app (#474).**
  - **Card address:** ChatGPT's card resources carry `ui.domain` and `openai/widgetDomain` as the API origin. Every other app gets neither, because Claude refuses to draw a card whose domain is not its own hashed `claudemcpcontent.com` form. With no domain, Claude gives the card an origin per conversation.
  - **Copy:** where the app is not proven to pass a result's `_meta` to a card (every profile but ChatGPT's, `passesResultMetaToCards`), `get_started`'s card copy also travels in `structuredContent`.
- Widgets not yet on the bridge use `window.openai` directly, including `toolOutput`, `toolResponseMetadata`, `callTool`, and `sendFollowUpMessage` where needed.
- **A preview card in an app that is not yet trusted with card-only tools** (every profile but ChatGPT's and Claude's, `honorsCardOnlyTools`) still shows **Send**. While the send rule is on, the server answers the card's `send_letter` or `send_postcard` as it answers the model there: not sent, with the link to the confirmation page where the person sends it. The card recognises that answer by its text, whether the host returns it as an error result or a rejection, and takes the page's `/confirm/` address for its own draft from it. It then shows **Open the confirmation page** in place of Send, with a note saying the mail is sent there, and the pill says **Send it on the confirmation page**. The button opens the page with `openLink`, or shows its address if the host does not open it. The state lasts while the card shows that draft. An answer without the address, or with another draft's, stays an ordinary failure. Claude has sent from the card since phase 2b (#474), because CLIENT-01 step 11 showed its model does not have the card-only tools.
- A result returned to a widget through `callTool` is visible to that widget only; the model never sees it (#366). On 2026-09-12 the checkout card created a checkout this way and the model could not name the order afterwards. Rule: every widget-initiated action leaves a customer-readable trace on the card (for a checkout, the order id and the purchase outcome), and nothing relies on `sendFollowUpMessage` to inform the model: `docs/learnings/generate-image-removal-decision.md` records that call resolving without posting the message on-device (2026-08-21). The conversation-side fallback is a read-only tool the model can call itself, which is why `list_orders` lists pack purchases (#365).
- ChatGPT implements MCP Apps too, and OpenAI's guidance is to use `window.openai` only for what the shared specification does not cover. For now the bridge keeps ChatGPT on `window.openai`, its proven path. Moving ChatGPT onto MCP Apps would be a separate, deliberate step.
- Widget resource metadata includes canonical `ui` metadata plus legacy `openai/*` aliases for compatibility. The connector detail panel renders our `ui.csp` back verbatim, which is how we know the canonical key is the one being read (issue #228).

### Content Security Policy

The declared policy (`WIDGET_CSP_CANONICAL` in `src/mcp/registerTools.ts`) allows
only what a widget genuinely loads: our API origin (the upload widget's
diagnostic beacon, and the temp-image URL the image card can fall back to),
OpenAI's static and user-content hosts, and as redirect targets: Stripe's checkout
host (plus our own checkout domain when `STRIPE_CHECKOUT_DOMAIN` names one, #373),
the letter-pack origin, and the API origin, which serves the purchase start page (#372). Everything else a widget displays is a `data:` URI produced
server-side, so it needs no host at all.

One host is **deliberately excluded**: the Azure blob host behind ChatGPT Library
picks. Trusting it would mean trusting all of Azure blob storage for a thumbnail
that the next screen renders anyway, so `ImageUploadCard` degrades to an
explanatory line instead. The picked image is unaffected - it reaches the server
over the `window.openai` bridge and is fetched from Node, outside CSP's reach.
See `docs/learnings/widget-csp-enforcement.md` for the evidence and for how to
reproduce enforcement locally (dev-mode ChatGPT never enforces it).

## UX and Safety Guidelines

- Never auto-send mail from a widget. Irreversible actions must stay behind explicit confirmation.
- Keep previews mobile-friendly and resilient to delayed or repeated render lifecycle events.
- Clearly show recipient context before confirmation when available.
- Prefer direct conversation image reuse or `imageUrl` handoff before opening the upload widget.

## Pay & Send Preview Actions

When prepaid balance is sufficient, letter and postcard preview widgets retain
their existing Send action. When it is insufficient, the widgets render the
server-provided alternatives:

- **Pay & Send** calls `create_mail_checkout`, displays the exact physical item
  and amount, and opens Stripe with `window.openai.openExternal`.
- **Buy a Letter Pack** calls `list_letter_packs`, replaces itself with one
  button per pack size showing letters and price, and each of those calls
  `create_pack_checkout` for that size. It no longer opens
  `LETTER_IRL_PACKS_URL`; that variable remains only as a website fallback.
  A website URL carries no identity, so a customer not signed in there bought
  letters that never reached the account the card could see.
- **Buy letters on the website** (#474) replaces both where the app takes no
  purchases (#475). There the server sends `payAndSend.available: false` and
  `letterPack.available: false`, with the website's letter packs page as
  `letterPack.purchaseUrl`. The card offers this button when that address is
  `https` and the host can open links. It opens the page with `openLink`
  (`ui/open-link` in Claude, which asks the person to confirm), then waits for
  the letters as after a pack checkout: the pill says **Waiting for your Letter
  Pack**, **Check status** appears, and `get_account_balance` is read again.
  When the host does not open the page, the card shows its address instead.
- **Pay & Send on letterirl.com** (#579) is offered for mail no pack pays for:
  a letter longer than one page, or a postcard other than 6x9.
  - The server marks such mail `sendEligibility.packPays: false`. Where the app
    takes no purchases, it also names the confirmation page in
    `payAndSend.pageUrl`, and that page takes the Pay & Send payment.
  - The card opens the page with `openLink`, shows the page's address if the
    host does not open it, and never offers a pack for such mail.
  - A balance the card has seen refreshed never turns Send on for it.
  - Where the app takes purchases (ChatGPT), the card's own Pay & Send is the way.
  - **Certified mail (#625)** is such mail whatever its pages. A preview that names `mailService` is marked `packPays: false`, so everything above holds for it; the studio's summary line names the service ("certified mail", or "certified mail with a return receipt"), its Delivery line is the server's `deliveryClass` ("USPS Certified Mail"; the disclaimer says it is signed for at delivery), and where the card sends the person to the page its note says "Certified mail is paid with Pay & Send on Letter IRL's page, which sends it once you pay." instead of the pack rule, which would contradict a one-page certified letter. The card reads the service from the preview it was shown, and from the terms of every later answer that carries them: the status (Claude, VS Code, where the card asks the server about its draft), and the answers to what the card does itself (a style, new words, the signature, a change of service). Each of those answers says how the letter travels with its terms (`mailService`, `deliveryClass`, `deliveryDisclaimer`), the style row keeps them with the terms (`travel`), and the card lays them over the preview's together, so the summary, the pay note, the Delivery line, the price and the buttons come from one answer and agree. An answer that says nothing of it (an older server, or an ordinary letter while certified mail is off) leaves the preview's. The style row refuses a status for another draft, while the card is setting a style, and for a preview that named no stationery, and then nothing of it is taken. A service the chat changed with `set_mail_service` is heard by a card shown its preview again, and by any card at its next answer to something the card does; a card that is never asked and does nothing (ChatGPT, whose card keeps its own state) does not hear a change the chat makes with any `set_*` tool. The server still decides what a send does: it refuses a send from the balance of a letter that is certified now, and a Pay & Send checkout prices the draft as it is now, so a certified preview that the chat turned back to ordinary and that is then paid for on a card that did not hear it checks out at the ordinary price and goes First-Class, as the person asked in the chat, while the card still says certified.

The note under the buttons describes the checkout only where the card can open
one. On the website path it says to sign in there with the same email, and
where nothing can be bought at all it is hidden.

After opening checkout, the widget refreshes `get_purchase_status` **only while
the document is visible**, and immediately when it becomes visible again.
Browsers throttle timers in a hidden iframe, and paying means being in another
tab, so a timer alone could not cover the window it existed for. Refreshing
stops once payment is confirmed: the remaining hop to provider acceptance is
owned by the hourly maintenance job, so there is nothing a short poll could
observe. A **Check status** button covers the rest, and webhook delay shows as
processing rather than failure. Stripe Checkout is reached as a redirect
target; the full widget policy is under [Content Security Policy](#content-security-policy).

## LetterHomeCard (conditional)

A seventh widget while `LETTER_IRL_HOME_ENABLED` is on: active drafts, recent mail and recent recipients, with explicit Refresh and website draft-review links.
