# Repository Guidelines

## Project Structure & Module Organization

Source TypeScript lives in `src/`. The runtime entry point is `src/mcp/httpServer.ts`; `src/server.ts` defines `LetterIrlServer` (tool registry and dispatch) and is imported by the entry point. Feature modules live under `mcp/`, `api/`, `services/`, `tools/`, `workers/`, `auth/`, `db/`, `store/`, `cli/`, `admin/` (the tailnet-only operator panel), `config/`, `content/`, `contracts/`, `logging/`, and `utils/`. Tool contracts are split across three files: `src/zodSchemas.ts` holds the Zod shapes that `src/mcp/registerTools.ts` registers, so it is the schema MCP clients actually receive; `src/schemas.ts` holds the JSON schemas on the tool definitions, from which `manifest.json` is generated; `src/mcp/toolSchemas.ts` types the registration maps and backs the schema-consistency tests. A schema change that should reach ChatGPT belongs in `src/zodSchemas.ts`, and a tool missing from the Zod maps in `registerTools.ts` is silently not registered. The full add-a-tool checklist is in `docs/tool-apis.md`. Automated tests live in `tests/` (Vitest); the top-level `test/` directory contains old one-off scripts and is not the test suite. SQL migrations are in `db/migrations/`. UI widgets are in `widgets/`. `manifest.json` is generated by `npm run manifest:generate`.

## Build, Test, and Development Commands

- `npm run dev`: Start the TSX watcher for local development.
- `npm run build`: Type-check and emit production JavaScript to `dist/`.
- `npm start`: Run the compiled HTTP API with Node.
- `npm run maintenance`: Run hourly maintenance once and exit.
- `npm run db:migrate:prod`: Apply pending migrations with compiled JavaScript.
- `npm run lint`: Enforce ESLint and Prettier.
- `npm test` / `npm run test:run`: Run the Vitest suite under `tests/`.
- `npm run verify`: Lint, build, unit tests and submission tests; mirrors the CI `checks` job.
- `npm run test:integration:local`: The real-PostgreSQL suites against a local database; mirrors the CI `postgres-integration` job.
- `npm run flow`, `npm run mcp:stdio`, `npm run mcp:http`: Local harness and transport commands.

## Coding Style & Naming Conventions

Use strict ESM TypeScript with two-space indentation. Prefer named exports; reserve default exports for single-entry files. Classes and interfaces use PascalCase, functions and variables use camelCase, and configuration constants use UPPER_SNAKE_CASE. Follow the existing camelCase role-based file names such as `creditService.ts`, `sendLetter.ts`, and `httpServer.ts`. Add comments only when behavior is not self-explanatory.

## Testing Guidelines

Add Vitest specs under `tests/unit/**` named `*.test.ts`, grouped by subsystem. Pair new logic with a happy-path test and at least one failure or recovery case. For mail delivery changes, cover duplicate/concurrent calls, provider timeouts, retries, and process recovery. Run lint, strict TypeScript, the full unit suite, and the relevant manual tests before opening a PR.

`npm run test:run` does **not** include the real-PostgreSQL ACID suite: it is opt-in behind
`LIRL_RUN_POSTGRES_INTEGRATION=true` and silently skips otherwise. CI
(`.github/workflows/ci.yml`) runs it on every pull request to `dev` or `master` in the
`postgres-integration` job, and asserts that the suites actually executed. For any change to
financial, fulfillment, refund, entitlement, migration, or admin state, run it locally before
opening the PR as well (`npm run test:integration:local` or `npm run test:integration:postgres`),
and report the pass count and the scenarios the change is covered by. Test files are never
type-checked: `tsconfig.json` includes only `src`, and Vitest strips types. A test that hand-builds a
dependency whose type has gained a field still compiles and fails only when it runs, which for the
PostgreSQL suites is usually first in CI. After changing a shared type, update every hand-built
instance under `tests/` in the same commit. See
[ACID Transaction Standard](docs/acid-transaction-standard.md) for the command and the canonical
lock order.

## Transaction Safety

ACID—Atomicity, Consistency, Isolation, and Durability—is the guiding engineering principle for every mutation of financial, balance, order, draft, fulfillment, refund, or administrative state. Follow the authoritative [ACID Transaction Standard](docs/acid-transaction-standard.md), including its transaction-boundary, idempotency, outbox, reconciliation, and PR-review requirements. Require risk-proportional local transaction, concurrency, and replay/recovery tests; when a PR changes an external boundary, require the applicable webhook, outbox, vendor-ambiguity, compensation, and reconciliation tests or a concrete N/A reason. External vendor calls cannot participate in a single PostgreSQL ACID transaction; model them as durable, resumable workflows.

## Commit & Pull Request Guidelines

Use short imperative commit summaries without trailing punctuation. PRs should describe behavior, link the issue when one exists, include test evidence, and call out migrations, environment variables, manifest changes, or external dependencies. Include screenshots or logs when a widget or protocol contract changes.

## Infrastructure Truths

Letter IRL uses one Railway project with separate `production` and `development` environments. The backend auto-deploys from `master` (production) and `dev` (development); the companion website auto-deploys from `main` (production) and `dev` (development). Production stays warm; development uses Railway Serverless and must retain it only while the documented wake-up acceptance checks pass.

Neon uses one project with isolated production and development database branches. Both environments use pooled Neon URLs and five-minute scale-to-zero. The API starts no database polling workers: confirmed sends use a transactional outbox and an hourly Railway cron runs recovery and maintenance. Temporary generated images use a private Railway bucket in cloud environments.

Preserve environment isolation and verify deployment assumptions against `docs/infrastructure.md`, `docs/deployment.md`, and `docs/railway-setup.md`.
